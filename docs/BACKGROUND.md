# 背景说明 — 我们在做什么、为什么、是什么

> CSCI 6806 Capstone · 给"没有上下文的人"看的科普版(配合结果版 `SUMMARY.md`)
> 主题:**vllm-ltr —— 用学习排序(Learning-to-Rank)优化 LLM 推理调度**

---

## 一、是什么(WHAT)

### 1. 问题:LLM 推理为什么会"堵车"?

当很多人同时向一个大语言模型(LLM)发请求时,服务器要把这些请求排队、分批送进 GPU 生成回答。问题在于:**不同请求的回答长度差别极大** —— 有的回一句话(几十个 token),有的写一篇长文(几千个 token)。

如果用最朴素的 **FCFS(先来先服务)**,一个"超长请求"排在前面,后面一堆"短请求"就得干等它 —— 这叫 **head-of-line blocking(队头阻塞)**。结果是:本来几十毫秒能答完的短请求,被迫等了几十秒。

### 2. 理论最优:SJF(最短作业优先)

调度理论早就知道:**让最短的作业先跑(Shortest-Job-First, SJF),平均等待时间最小**。如果我们能让"短回答"的请求插队到前面,队头阻塞就消失了。

**但有个致命问题:请求还没生成,我们根本不知道它的回答会有多长。** SJF 需要"作业长度"这个信息,而推理时这个信息是未知的。

### 3. vllm-ltr 的核心思路:预测长度 → 近似 SJF

vllm-ltr(Fu et al. NeurIPS'24,基于 vLLM 0.4.1)给出的答案是:

> **训练一个轻量的"输出长度预测器",在请求进队列时先估一下它大概会生成多长,然后按"预测短的优先"来调度。**

这样就用一个**预测**近似了那个拿不到的"真实长度",把 SJF 落地了。预测器不需要很准 —— 它只要能**把请求按长度大致排对序**就行(这正是 **Learning-to-Rank / 学习排序** 的目标:不预测绝对值,只预测相对顺序)。

衡量"排序排得好不好"的指标是 **Kendall's Tau**(0=乱排,1=完美排序)。

## 二、为什么(WHY)

### 1. 为什么选这个题目?
- **现实痛点**:LLM 推理服务(ChatGPT 这类)的延迟和成本,很大一部分耗在调度上。一个不改模型、不加硬件、只改调度顺序就能降延迟的方法,**性价比极高、落地价值大**。
- **可复现**:有公开论文 + 开源 fork,适合 capstone 在单卡上复现 + 做出自己的改进。

### 2. 为什么不只复现,还要"优化"?
论文方法有个公开承认的弱点:**预测器会过拟合训练分布**。在训练用的数据集(LMSYS)上排序很准,换一个没见过的数据集(ShareGPT)就明显变差 —— 这叫 **generalization gap(泛化差距)**。一个只在自家数据上灵的调度器,实际部署会打折扣。所以我们的优化目标聚焦在 **缩小这个泛化差距**。

### 3. 为什么用 PARS / 为什么做这些实验?
- **PARS**(Tao et al. 2025):一个更新的排序训练法,用 **pairwise margin loss(成对间隔损失)+ 更强的 BERT backbone + delta-filter(过滤噪声样本对)**。我们把它实现进这个 fork,看能否比原版 listMLE 泛化更好。
- **为什么测 in-dist vs cross-dist**:只有同时报"自家数据"和"陌生数据"两个分数,才能诚实地衡量泛化,而不是自吹自家数据上的高分。
- **为什么做 ablation(消融)**:PARS 改了三样东西(loss / backbone / filter)。如果只说"PARS 更好",无法回答"到底是哪一项起作用"。我们把三项拆开各训一个变体,**诚实地定位真正的功臣**(结果发现是 BERT backbone,不是 loss/filter —— 这是个有价值的负结果)。
- **为什么对比分类(classification)**:base paper 主张"排序 > 分类"。我们自己训一个分类预测器验证这个主张,而不是照搬结论。

## 三、做了什么(HOW / 三条主线)

### 主线 A — 复现 baseline
自己(不用作者预训练权重)跑通整条链路,在 6 档负载下对比 **FCFS vs LTR** 的延迟。
→ 验证:高负载下 LTR 确实把队头阻塞(TTFT)大幅压下来。

### 主线 B — 自训预测器 + 实现 PARS
从零训练三个长度预测器,横向比排序质量(Kendall's Tau):
- **listMLE**(OPT-125M)—— 复现论文的排序 baseline
- **classification**(OPT-125M,分 10 个长度桶)—— 验证"排序 vs 分类"
- **PARS**(BERT-base,我们移植实现)—— 优化尝试

### 主线 C — 泛化性研究
- **Generalization gap**:测每个预测器在 in-dist(LMSYS)和 cross-dist(ShareGPT)上的 Tau,看掉多少。
- **Ablation**:拆解 PARS 的三要素,定位真正带来跨分布增益的因素。

> 具体数字、表格、结论见同目录 **`SUMMARY.md`**。
> 一句话结果:LTR 高负载 TTFT 加速 ~2.9×;排序 Tau(0.55-0.60)≫ 分类(0.19);PARS 跨分布 +15%,但增益主要来自 BERT backbone(诚实负结果)。

## 四、关键名词速查

| 名词 | 一句话解释 |
|---|---|
| **Head-of-line blocking** | 队头一个长请求,堵住后面所有短请求 |
| **SJF(最短作业优先)** | 理论最优调度:短的先跑,但需要知道长度 |
| **Learning-to-Rank(LTR)** | 不预测绝对长度,只学"谁比谁短"的相对顺序 |
| **预测器(predictor)** | 请求进队列时估其输出长度的轻量模型(OPT-125M / BERT) |
| **Kendall's Tau** | 排序质量指标(0 乱排 ~ 1 完美) |
| **TTFT / TPOT** | 首 token 延迟 / 每 token 延迟 —— 排队 vs 生成两类延迟 |
| **Generalization gap** | 训练分布 vs 陌生分布上的性能差 = 过拟合程度 |
| **PARS** | 一种更新的排序训练法(margin loss + BERT + delta-filter) |
| **Ablation(消融)** | 逐个关掉某个组件,看它到底贡献多少 |
